# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ops-dashboard`: a Spring Boot REST API (read-only JSON under `/api`) plus a plain-JavaScript page in `src/main/resources/static/` that draws KPI tiles, two inline SVG charts, a late-deliveries table and a vendor list. The repo is also the material for a Claude Code workshop (`workshop/`, `docs/`); tickets live in `docs/tickets/`.

## Commands

```bash
SPRING_PROFILES_ACTIVE=demo ./mvnw spring-boot:run   # run on in-memory H2, no Docker; http://localhost:8080
docker compose up -d db && ./mvnw spring-boot:run    # run on PostgreSQL 16 (default profile)

./mvnw test                                          # Java: 25 tests, always on H2 (demo profile)
./mvnw test -Dtest=DashboardControllerTest           # one class (append #methodName for one test)
npm install && npm test                              # Frontend: 45 tests, Jest + jsdom
npx jest src/test/javascript/render.test.js -t "name" # one file / one test
```

There is no lint or build step for the frontend. CI is not enabled; `docs/examples/ci.workflow.yml` is the template.

## Architecture

- **Pinned clock.** "Today" is `ops.today=2026-09-21` (`application.properties`), exposed as a fixed `Clock` bean in `ClockConfig`. Every default range ("last 30 days ending today"), every "days until" figure, the frontend (it reads `today` from `/api/health`), and every test assertion depends on it. Never use the real system date.
- **Backend flow.** Controller → `DateRange.resolve(from, to, clock)` → `DashboardRepository`/`VendorRepository` (plain SQL via `NamedParameterJdbcTemplate`, no JPA) → response records. Counting conventions are documented at the top of `DashboardRepository`. `DateRange` deliberately has no validation (TODO-232).
- **Schema and data** come only from Flyway (`db/migration/V1__schema.sql`, `V2__seed.sql`). `V2__seed.sql`, `docs/data/*.csv` and the answer key are generated by `tools/make_seed.py`; regenerate rather than hand-edit.
- **Frontend.** `app.js` is one IIFE; all logic is inside `initApp(document, fetchImpl)`, and the module exports to `module.exports` under Node so Jest can load the same file. API client (`createApi`) → `state` → render functions. No framework, no build, no colours outside `style.css`.
- **Frontend test harness** (`src/test/javascript/setup/loadApp.js`): `loadApp(overrides)` injects `index.html`'s body into jsdom, swaps `fetch` for an in-memory fake API serving `FIXTURES` (numbers match the real seed), records calls in `api.calls`, and can fail paths via `{ failing: ['/api/kpis'] }`.
- **Element ids must be registered.** `harness.test.js` fails if `index.html` contains an id not listed in `REGISTERED_IDS` in `loadApp.js`. Add every new id there.

## Rules

- `pom.xml` dependencies are frozen. Any change needs a CHG ticket.
- No new npm dependencies without being asked.
- Before declaring work done: run both `./mvnw test` and `npm test` and report both counts.
